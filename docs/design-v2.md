## 1. 产品定位与能力边界

### 1.1 一句话

**refactor-pilot：输入一个本地项目路径，自动完成「审计 → 规划 → 分阶段改造 → 验证」的全流程托管，产出可直接粘贴给 AI CLI 执行的指令块。**

### 1.2 解决的问题

用 AI CLI 改造既有项目时，规划者要反复做同样的二十件事（依赖闭合、命名核对、约束沉淀、提交拆分、阈值实测……），枯燥且易漏，漏一项返工一轮。

refactor-pilot 把这部分自动化：**人只回答一份开头问卷，之后每次运行工具，它就告诉你「现在该做什么」并给出完整可粘贴指令块。**

### 1.3 不做

- 不自己写业务代码（交给 CodeBuddy 等 AI CLI）
- 不调用 AI API（首版）
- 不做文档生成与发布（S6/S7 首版 alpha，默认跳过）

### 1.4 ⭐ 能力边界：三类问题的覆盖声明（写进 README 第一句）

静态规则的能力天花板是**静态可证**。源项目最有价值的产出恰恰是第三类——这不是缺陷，但必须如实标注。

| 类别           | 例子                                                        | 静态规则能否捕获       | 覆盖策略                                     |
| -------------- | ----------------------------------------------------------- | ---------------------- | -------------------------------------------- |
| **工程化缺失** | 零测试、无依赖声明、无 lint 配置                            | ✅ 能                   | 规则全开，应高召回                           |
| **配置矛盾**   | 多处定义同一键但值不一致                                    | ⚠️ 勉强（低置信启发式） | 报告但标注置信度                             |
| **语义正确性** | 逻辑/数值层面的错误（具体实例见基线清单，**不写入本文档**） | ❌ 不能                 | **不覆盖**；唯一手段是 Q6 对拍或人工深度审计 |

**定位原话（建议 README 首句）**：

> refactor-pilot 是一个**工程化补课工具**。它能可靠发现工程化缺失；它能提示配置矛盾；它**不能**验证语义正确性——后者只有开启对拍（Q6）或人工深度审计才能覆盖。

**理由**：本工具的精神内核是"可验证"。如果它夸大自己的能力，就重蹈了它要解决的那个问题的覆辙。

### 1.5 ⭐ 不覆盖声明：Q6 无解时必须显式输出，绝不静默跳过

**【必须遵守】**

绝大多数项目没有参考实现。此时工具**必须**在 S1 扫描结果与 S2 审计报告**开头**原样输出下列声明：

```
本项目未检测到可用的参考实现，语义正确性无法自动验证。
以下类别不在本工具覆盖范围内：
  - 逻辑与数值正确性
  - <其余按规则包动态列举>
需通过人工深度审计或提供参考实现（Q6）后重跑。
```

**理由**：静默跳过会让用户误以为"没报问题就是没问题"——**这正是本工具要解决的那个毛病**。

**判定"无参考实现"**：`scan.q6_signals` 中未检测到「只读参考目录 / 对拍类测试 / 数值基线文件」三者中的任何一个。

> 声明放在**开头**而不是末尾——末尾没人看。

### 1.6 ⭐ 召回率自检是一等公民，不是 alpha

**【必须遵守】**

`refactor-pilot recall` 子命令与 S1/S2 同等地位。理由：**召回率是唯一能证明规则库有效的手段**，没有它，S4/S5 的设计全部建立在未经检验的地基上。

## 3. 七阶段架构：输入 / 输出 / 检查点

### 3.1 全局不变式 **【必须遵守】**

1. **单步推进**：每次运行最多推进一格；任一检查点不过，停在原格输出修复指令，绝不推进。
2. **事实优先**：进度判断以「仓库事实 + 落盘证据」为准，不依赖人转述，不解析 AI 会话。
3. **失败即停**：任何自动检查抛错，输出诊断 + 修复指令块，不改状态。
4. **工具不写业务逻辑**：唯一例外是确定性机械变换（见 5.2 第一刀），且限于 safe 级。

### 3.2 总表

| 阶段               | 输入                              | 输出（落盘）                                                 | 检查点（Gate）                                               |
| ------------------ | --------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| **S1 扫描**        | 项目路径、`--ref`、可选已有 state | `.upgrade/scan.json`                                         | 语言在支持集内；测试/lint 命令**实测可用**（默认不实测，见 12.5）；git 仓库可用 |
| **S2 审计**        | scan.json + 规则包                | `.upgrade/audit.json` / `audit.md`                           | 每条 finding 必须带 `file:line`；无证据降级 `unverified`     |
| **S3 问卷**        | audit.json + 默认策略             | `.upgrade/brief.json`                                        | 必答非空；冲突矩阵无矛盾；仅执行一次                         |
| **S4 规划**        | scan + audit + brief              | `.upgrade/plan.json`                                         | 依赖闭合、无环、每阶段可独立验收、零 orphan                  |
| **S5 改造**        | plan + state + 仓库事实           | `.upgrade/steps/<stage>.md`、`.upgrade/evidence/<stage>.log` | 七格门：A→B→C→D→E→F                                          |
| **S6 文档** ★alpha | plan + git log                    | `.upgrade/draft/README.md`、`CHANGELOG.md`                   | 默认跳过；产物标 `DRAFT`，不覆盖原文件                       |
| **S7 发布** ★alpha | plan + 仓库事实                   | `.upgrade/release_checklist.md`                              | 默认跳过；只生成清单与命令，不执行不可逆操作                 |

### 3.3 S1 扫描产出字段族 **【建议】**

- `lang`：语言与运行时（首版 Python）
- `layout`：包根与模块树，入口脚本
- `toolchain`：`test_cmd` / `lint_cmd` / `fmt_cmd` / `type_cmd` —— **探测不到置 `null` 并标 `degraded`，绝不编造命令**
- `vcs`：分支、工作树是否干净、remote、`git rev-list --count HEAD`
- `constraints_file`：候选约束文件（`CODEBUDDY.md` / `AGENTS.md` / `CLAUDE.md`）
- `hooks`：pre-commit 是否存在、hook 与本地工具版本是否隔离
- `q6_signals`：是否存在只读参考目录 / 数值密集代码 / 对拍类测试（用于 Q6 默认值与 1.5 的声明）
- `q2_candidates`：禁改路径候选（见 6.1）

### 3.4 S2 审计产出结构 **【必须遵守】**

```json
{"id":"A-013","rule":"A01","class":"engineering","severity":"blocker",
 "file":"src/acme_core/pipeline.py","line":42,"evidence":"def normalize(...): ...",
 "suggestion":"实现或删除存根","confidence":"high"}
```

- 分级：`blocker` / `major` / `minor` / `info`
- 置信度：`high`（静态可证）/ `medium`（启发式）/ `low`（仅提示）
- 类别：`engineering` / `config` / `semantic`（第三类默认不产出自规则，仅用于基线对照与豁免声明）
- **每条 finding 必须带 `file:line` 证据**，带不出证据的一律降级 `unverified`，不计入 blocker

## 4. R1–R10 在 S5 中的触发时机

| 规则                 | 触发格                            | 工具自动做的                                                 | 注入指令块的                                         | 工具如何判定"做到了"                                         |
| -------------------- | --------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------------------ |
| **R1 依赖闭合**      | A                                 | 对 writes 做 import→定义追溯，生成依赖状态表                 | 状态表 + "未闭合则中止，先补实现"                    | 状态表无 `stub` 行；若有 → 插入前置补实现阶段                |
| **R2 命名核对**      | A                                 | 解析存根符号名/签名/`__init__` 导出，生成契约快照            | 快照 + "沿用已有名字，指令只描述行为"                | A 格只读；**D 格反向查：新增顶层符号超出快照 → warn 不 block**（见 4.1） |
| **R3 约束沉淀**      | S5 首次进入前（一次性）+ 每格开头 | 写入约束文件**顶部**并加锚点注释                             | 每格指令块第一行是 grep 验证命令                     | 锚点存在且条数匹配                                           |
| **R4 实跑验收**      | D                                 | 拼装验收命令（test + lint + e2e）                            | 命令 + **强制输出重定向到 evidence log**             | 读 log：exit code + 关键行 + 用例数                          |
| **R5 提交拆分**      | E                                 | 按改动路径分类 commit_type，生成逐条 `git add <path>`        | 逐类 add + 完整 message；明令禁 `git add -A`         | `git status --short` 为空 且 `rev-list --count` +1           |
| **R6 编号归属权**    | 全格（尤其 E）                    | commit message 由工具按 plan 编号全文生成                    | "复制下列 message 原文，不要用你自己建议的编号"      | subject 与工具生成字符串逐字一致                             |
| **R7 阈值实测**      | C（条件格，Q6 启用则**强制**）    | 生成测量调用，要求打印实测值 + 参考量级                      | "先测量贴回数据，不要自定阈值"                       | 读 `measure.json` 后计算阈值与余量倍数，标出余量最小项       |
| **R8 push + 三查**   | F                                 | 拼装 `status --short && du -sh .git && rev-list --count HEAD` | 三条命令 + push                                      | 本地 HEAD == 远端 tracking ref                               |
| **R9 网络失败**      | F 失败时                          | 检测 push 后 HEAD 与远端一致性                               | 重试指令 + 禁改 remote / 强推 / 重写历史 / 删 reflog | 重试后一致；连续失败则建议延后下一轮                         |
| **R10 过滤 AI 建议** | A（硬约束）+ E（清单）            | 生成禁改路径清单、自检清单                                   | 不推荐指令/不自定编号/不改公共契约/不顺便改 X        | 无法自动检测 → 以清单形式交人做门禁                          |

### 4.1 R2 的 D 格反向查：warn 而非 block **【必须遵守】**

**规则**：D 格校验时，若发现新增顶层符号超出 A 格契约快照，**只提示、不阻断推进**。

提示措辞固定为：

```
以下新增顶层符号不在原契约快照中：
  - <symbol>（<file>:<line>）
请说明为什么不能沿用现有名字。
（若为辅助函数/私有符号，可说明后继续；本项不阻断推进。）
```

**理由**：实现存根时新增辅助函数、私有符号**几乎必然发生**，判定为 block 会让每个阶段都卡住——这是典型的"规则正确但代价过高"。

**warn 也要留痕**：warn 项写入 `.upgrade/evidence/<stage>.naming_warn.json`。理由同 waivers——事后要能查"当时为什么加了这些名字"。

### 4.2 三条关键机制 **【必须遵守】**

**① 证据落盘协议（让"进度自检查"真正可行的前提）**

```bash
<test_cmd> 2>&1 | tee .upgrade/evidence/<stage_id>.log
```

D 格验收一律强制重定向。工具下次运行读 log 判定 exit code、用例数、是否"静默选 0 个用例"。**没有证据文件即判定未完成。** 这条不做，决策 6 就是空话。

**② R3 用锚点注释而非关键词 grep**

```markdown
<!-- RP:CONSTRAINT:C01 --> 不得修改 <forbidden_paths>，确需改动先停下来说明原因
```

按 ID 计数。grep 关键词会因措辞变化误判"约束丢了"→ 假失败。

**③ R1/R2 分工**：机械部分（存根检测、符号提取、导出清单）工具做；语义部分（依赖是否真的够用）交 AI 只读核对。A 格明确禁止改代码。

**冲突矩阵（S3 必须校验）** **【必须遵守】**

- Q3=严格兼容 且 Q1=架构重构 → 警告，要求确认
- Q4=阻塞清零 且 Q5=覆盖率阈值 → 警告（阶段数显著拉长）
- Q6=需要对拍 但未提供参考来源 → 拒绝，退回重答
- Q6=不需要 且 Q5=与参考实现对拍 → 矛盾，拒绝
- Q4=阻塞清零 且存量 > 阈值 → **插入清理阶段，不是豁免**（见 5.2）

### 5.2 存量清理三刀切（Q4=阻塞清零时）**【必须遵守】**

```
第一刀：能否自动修复 —— ruff check --fix / ruff format 能清的，
        合并成一个「机械阶段」，工具直接跑命令，不经过 AI
第二刀：剩余需人工判断的，按错误类型拆（unused / type / style）
第三刀：类型内文件数仍超上限，再按目录拆
```

**关键在第一刀**：可自动修复的错误占存量大头却完全不需要 AI。先机械清掉，剩下的才需要分阶段。

**机械阶段的四条护栏** **【必须遵守】**

1. **机械阶段后强制重扫**：删除 import 会改变 import 图（影响 A04/D01/D04）；format 会使所有 `line` 证据失效
2. **只跑 safe fixes**；`--unsafe-fixes` 需问卷显式开启
3. **排除 `__init__.py` 的 F401**：那里的 import 常是再导出，删了直接破坏公共契约，与 Q3=严格兼容冲突
4. **格式化单独 commit**；建议生成 `.git-blame-ignore-revs`（P2）

**机械阶段的 stage 类型**：`stage.type ∈ {mechanical, ai}`。机械阶段跳过 A/B/C 格，直接 `run → verify(D) → commit(E) → push(F)`。

**永久豁免必须留痕**：豁免项写入 `.upgrade/waivers.json`，格式 `{rule_id, file, reason}`，否则无人知道豁免了什么、为什么。

> **G07 的产物 pattern**：`__pycache__/`、`*.py[cod]`、`.venv/`、`venv/`、`.mypy_cache/`、
> `.ruff_cache/`、`.pytest_cache/`、`.tox/`、`*.egg-info/`、`build/`、`dist/`。
>
> **为什么必须做成规则**：`.gitignore` 是事后补丁 —— 前提是"记得先写"。
> 典型事故就是新项目 `git init` 后直接 `git add -A`，把一堆 `.pyc` 提交了，
> 事后才补 `.gitignore`（但已跟踪的文件不会因补规则自动消失，还得 `git rm --cached`）。
> 这类问题靠人记住不可靠，正该由工具兜住。
>
> 检测口径：`git ls-files` 的结果逐条比对上述 pattern（只看已被跟踪的，
> 未跟踪的产物文件由 G05 负责）。每条命中给出文件路径作为 `file` 证据。
>
> **历史版本也要能查**：产物被"事后补 `.gitignore` + `git rm --cached`"清掉后，
> 当前树里查不到，但**历史里确实跟踪过**。核查配方支持 `--rev <ref>`
> （`git ls-tree -r --name-only`），这条规则的有效性演示就是这么来的。
>
> **受 G05 抑制**：`.gitignore` 缺失或未忽略这些 pattern 时，G07 不再逐条产出，
> 而是合并进 G05 的一条 finding（同上模式，见 7.4）。两者的关系与 C01→D01 同类：
> 母规则命中时子规则**必然**命中，逐条列只会制造冗余。
>
> #### G05 的 pattern 必须分级 **【必须遵守】**
>
> 一层平铺的 pattern 清单会误报：v1 用的是标准 GitHub Python 模板（有 `__pycache__/`、
> `*.py[cod]`、`build/`、`dist/`、`*.egg-info/`、`.venv/`），却因为"缺 `.mypy_cache/`
> `.ruff_cache/` `.pytest_cache/` `.tox/`"被报 —— 而这个项目**根本没用这些工具**。
>
> | 层     | pattern                                                      | 缺失时              |
> | ------ | ------------------------------------------------------------ | ------------------- |
> | **核心** | `__pycache__/`、`*.py[cod]`、`build/`、`dist/`、`*.egg-info/`、`.venv/` | 直接报 **major** |
> | **可选** | `.mypy_cache/`、`.ruff_cache/`、`.pytest_cache/`、`.tox/`     | **仅当检测到对应工具在用**才报 **minor** |
>
> "在用"的证据：有对应配置文件（mypy/ruff 配置、`pytest.ini`、`tox.ini`）、
> 或 pyproject 里有对应 `[tool.*]` 段、或（pytest 这条）仓库里存在测试文件。
>
> ⚠️ **G07 不分级**：G07 查的是"已经被跟踪的产物文件" —— 无论仓库用不用这个工具，

#### `class` 的判据 **【必须遵守】**

> **缺东西 = `engineering`，值对不上 = `config`。**

| 写法 | class | 例 |
| ---- | ----- | -- |
| 某文件/配置/测试**不存在** | `engineering` | B01 无测试、C01 无依赖声明、C02 无 lint、C04 无约束文件、C05 hook 未隔离、C06 无 CI |

⚠️ **这条不是分类癖好，是统计口径**：10.6 的「工程化召回率 = L1命中 ∩ engineering / L1总数 ∩ engineering」
若把缺失型规则全标成 `config`，分子分母恒为 0 —— 这一列**永久失效**，
而且不报错、测试全过、数字看着正常（实测踩过，见 process.md P-14）。

### 7.4 ⭐ 规则抑制关系（suppression edges）**【必须遵守】**

**问题**：某些规则在"母规则"命中时会退化成噪音。
典型：**项目没有任何依赖声明文件（C01 命中）时，D01（三方 import 未声明）会对每一个 `import torch` / `numpy` / … 全部触发**，产出几十条与 C01 完全冗余的 finding，淹没报告。

**机制**：声明抑制边 `母规则 → 子规则`。母规则命中时，子规则**不逐条产出**，而是合并计一条。

| 母规则                    | 抑制                          | 合并后的输出                                                 |
| ------------------------- | ----------------------------- | ------------------------------------------------------------ |
| **C01**（无依赖声明文件） | **D01**                       | 单条：`C01` 命中，且检测到 N 个未声明的三方 import（不逐条列） |
| **C01**（无依赖声明文件） | **A04 的解析方式** ⭐         | 见 12.13：切到 **script-style 解析**，兄弟目录与入口目录里的模块都算合法 |
| **C06**（无 CI 配置）     | **B06**（测试未在 CI 中执行） | 单条：`C06` 命中，故测试不可能在 CI 中执行                   |
| **B01**（无测试文件）     | B02/B03/B04                   | 自然不产出（这些规则以测试文件存在为前提），显式声明以防实现时漏判 |
| **C02**（无 lint 配置）   | E03 类委托规则                | 改报"lint 未接入"，不报具体代码卫生问题                      |
| **G05**（`.gitignore` 缺失或未忽略常见产物） | **G07**（仓库跟踪了本该忽略的产物文件） | 单条：`G05` 命中：`.gitignore` 未忽略 N 个常见 pattern，且仓库中已跟踪 M 个此类产物文件 |

**为什么做成显式声明而不是让它自然发生**：B01 那几行确实会自然不产出，但 C01→D01 不会——不声明的话，扫描器会老实地产出 40 条 D01，报告直接不可用。
**显式列表还能在新增规则时起到提醒作用**：加规则时要问一句"它有没有母规则"。

**抑制不等于丢失信息**：被抑制的子规则仍计数，以"N 个"的形式出现在母规则的 finding 描述里。

#### 12.13 ⭐ A04 的 script-style 解析 **【必须遵守】**

**问题**：A04 用"包路径解析"去判一个**脚本型仓库**，会全军覆没。实测 v1：33 条 A04 候选，
**全部是误报** —— `from language_module import GPTModel` 里的 `language_module.py`
就躺在同一个目录里。

**根因**：`python src/modules/x.py` 会把脚本所在目录放进 `sys.path[0]`，
所以脚本型仓库里的兄弟 import **完全合法**。仓库没有打包声明（C01 命中）时，
"包路径"这个概念根本不存在。

**机制**：C01 命中 → A04 切换解析方式（按以下顺序，命中即合法）：

```
1. 兄弟解析   ：{import 所在目录}/{target}.py 存在 → 合法（脚本型的核心规则）
2. 入口目录解析：脚本所在目录视为 source root → 合法（P-03 / 12.12②）
3. 打包声明的 source root 别名（若存在）
4. 都不中 → 才报 A04
```

第 1 条消掉 v1 `archives/` 下的 9 条，第 2 条消掉 `src/modules/` 下的 15 条。
**打包声明存在时不启用 1、2** —— 有打包声明就意味着项目按包组织，那时兄弟 import
是真的错（也是 I 组要管的契约问题）。

## 8. S4 切分算法（已设计，首版不实现）

### 8.1 数据结构

```
Atom:  {id, kind, files[], rule_ids[], sev}     # 文件 × 改动类型
Stage: {id, title, type(mechanical|ai), atoms[], writes[], forbidden[],
        depends_on[], acceptance[], commit_type, needs_measure, status, step}
Plan:  {brief_hash, audit_hash, stages[]}
```

**为什么用「文件 × 改动类型」做原子**：以 finding 为原子太碎（一个文件被切成 6 个阶段），以文件为原子太粗（无法做到"一个 commit 一类改动"）。

### 8.2 主流程（伪代码）

```
function plan(scan, audit, brief) -> Plan | ConflictReport:

  # 0. 冲突预检：禁改路径 vs 必改项
  conflict = [f | f.sev==B and f.file ∈ brief.forbidden_paths]
  if conflict: return CONFLICT_REPORT   # 解除禁改 或 写 waiver

  # 1. findings → atoms（同文件同 kind 合并）
  atoms = merge_by(file, kind)(findings_to_atoms(findings))

  # 2. 存量清理三刀切（见 5.2），排在所有写代码阶段之前
  if brief.q4 == BLOCK and scan.lint_backlog > 0:
      stages += make_mechanical_stage(auto_fixable)          # 第一刀
      stages += make_stages(split_by_error_type(rest))       # 第二刀
      stages += make_stages(split_by_dir(overflow))          # 第三刀
      # 机械阶段后强制重扫

  # 3. 依赖图（依赖闭合的规划期版本）
  G = build_graph(atoms, scan.import_graph, scan.stub_set)
  #   建边 a→b（a 先于 b）：
  #   (a) b 所在模块 import 了 a 写的符号且该符号当前是存根 → 强制
  #   (b) a、b 写同一文件 → 串行
  #   (c) a 改公共契约（Q3=可改）→ b 是调用方同步 → 强制
  #   (d) b 是 a 的验收测试 → 强制
  if has_cycle(G): return CYCLE_REPORT(min_cycle(G))

  # 4. 拓扑分层（Kahn） → 5. 层内聚类（目录邻近/同规则组/同 commit_type）
  # 6. 依赖闭合校验：unresolved → 插入补实现阶段
  # 7. 验收命令挂载：挂不上 → needs_manual_acceptance，阻塞
  # 8. orphan 检查：{B,M} 级 finding 未被任何 stage 覆盖 → ORPHAN_REPORT
  # 9. 规模检查：> MAX_STAGES（默认 12）→ WARN
  # 10. 编号冻结 + 返回 Plan
```

### 8.3 硬约束

| 约束   | 内容                                                         | 违反时                                       |
| ------ | ------------------------------------------------------------ | -------------------------------------------- |
| C1     | 单阶段 writes ≤ `MAX_FILES=8`                                | **软警告**（代理指标，待实测校准，决策 #17） |
| C2     | 单阶段只产生一类 `commit_type`                               | 拆（R5 的规划期保障）                        |
| C3     | 阶段内依赖要么本阶段闭合、要么此前已完成                     | 插入补实现阶段                               |
| **C4** | 每个阶段必须挂至少一条**具有针对性**的验收命令（能观测本阶段改动；全量测试仅作兜底） | 与相邻合并；仍不行则阻塞                     |
| C5     | `writes ∩ forbidden = ∅`                                     | 冲突报告，退回                               |

### 8.4 两个定死的细节

**① `implemented_before(s)` 判定**：= `scan.stub_set` 里没有它 **且**（它是仓库既有代码 **或** 已排在前面的阶段的 writes 覆盖了它）。后者不能漏——否则重规划会把刚写完的代码又判成存根。

**② 增量重规划时编号稳定**：已完成阶段 `id` **冻结不变**（否则历史 commit message 与 plan 对不上）；新插入阶段放未完成区最前，命名 `S{n}-{suffix}`。

## 10. 召回率方法论

### 10.1 陷阱 1：审计快照与基线采集对象必须一致

**本用例（源项目 v1）不适用该风险**：v1 从未被改造过（v2 是完全独立的新仓库，不是 v1 的分支），v1 当前 HEAD 即基线采集对象，直接审计即可，`--ref` 非必需。

**但换到其他项目时必须先判定**：若目标仓库 HEAD 已改造完成，而基线采集自改造前，直接跑当前 HEAD = 扫"问题已被修好的代码"，召回率必然接近 0，**而这个 0 是假的**。
最危险的后果是误判"规则库不行"，砍掉一堆正确的设计。

**判定与解法**：跑之前先确认 HEAD 是否已是改造后状态；若是，必须用 `--ref` 在改造前快照上只读审计。

### 10.2 陷阱 2 与 3

**陷阱 2：误报率的分子需要人工定性。** "工具报了但基线没有"未必是误报——可能是真问题但基线漏了。所以第三列应叫**"未匹配"**，再由人定性为真阳性 / 误报。直接叫"误报率"会让数字虚高。

**陷阱 3：基线本身可能有错。** 人工清单也会分级不准、也会遗漏。每项需带 `baseline_confidence`，允许标"存疑"。

### 10.3 匹配规则必须事先定死 **【必须遵守】**

**按 `rule_id` + `file` + `证据文本` 三者匹配，不按 line。**

- `rule_id`：以 `baseline.json` 的 `detectable_by` 显式映射为准（主）
- `file`：相对路径，需容忍机械阶段后的重命名（记录 `file_aliases`）
- `证据文本`：代码片段/符号名，**做归一化后比对**（去空白、去注释）

**证据文本允许被 `--fix` 改写**，因此基线必须来自机械阶段之前的快照（见 10.4）。

**绝不按 line 匹配**：机械阶段跑完后 line 必然位移，按 line 匹配会让召回率**假性下降**——这是自伤，而且极难发现（数字难看，你会去找规则的毛病，而不是匹配器的毛病）。

**绝不做模糊匹配**：模糊匹配能让召回率好看，但那是自己给自己打分。

`baseline.json` 中的 `line` 字段**仅作人工定位用，不参与匹配**。

#### 匹配分叉：缺失型 vs 存在型 **【必须遵守】**

基线条目的 `file` 字段有两种取值，匹配方式不同：

| 类型       | `file` 取值特征                                              | 例子      | 匹配方式                                           |
| ---------- | ------------------------------------------------------------ | --------- | -------------------------------------------------- |
| **缺失型** | 目录/通配符/**概念性占位**（`(无 lint 配置文件)`、`CODEBUDDY.md / AGENTS.md / CLAUDE.md`、含 `(需核对)` 的模糊路径） | K-01~K-05 | **只按 `rule_id` 匹配**，file 与 evidence 均不参与 |
| **存在型** | 真实相对路径 + 有 `evidence`                                 | 补充条目  | `rule_id` + `file` + `evidence` 三者匹配           |

**为什么必须分叉**：概念性占位无法与工具输出的 `file` 字段比对（工具报 C02 时 file 填什么？两边若不一致就判成漏报，而这是**匹配器的锅，不是规则的锅**）。

**约定**：`detectable_by` 非空且 `file` 为占位值 → 自动判定为缺失型，走 rule_id 单键匹配。

### 10.4 ⭐ 硬要求：基线必须采集于机械阶段之前 **【必须遵守】**

> **召回率基线必须采集于机械阶段之前，或采集自 `--ref` 快照。**
>
> 原因：机械阶段（ruff `--fix` / `format`）会删除或修改被审计的代码行本身，
> 导致 `rule_id + file` 对得上、但证据文本已被改变，从而被判为漏报——
> **这是一种不会报错、只会让数字悄悄变差的假性漏报。**
> 基线一旦污染，只能重新人工采集，代价极高。

**本用例（源项目 v1）天然满足**：v1 从未被改造、机械阶段从未在其上跑过，当前 HEAD 即"机械阶段之前"的状态。

### 10.5 ⭐ 分层统计：先分覆盖范围，再算召回率 **【必须遵守】**

**每一条基线条目先归层，再决定进不进分母。**

| 层                      | 判据                                                        | 进分母？     |
| ----------------------- | ----------------------------------------------------------- | ------------ |
| **L1 规则范围内**       | `detectable_by` 非空 **且** 对应规则已在首版实现            | ✅ 进         |
| **L2 规则未实现**       | `detectable_by` 非空，但对应规则是 P1/P2 或不在首版五组内   | ❌ 不进，单列 |
| **L3 无规则（能力外）** | `detectable_by` 为空数组                                    | ❌ 不进，单列 |
| **L4 基线存疑**         | `baseline_confidence = low`，或标 `(需核对)` 且路径无法落实 | 计入但标注   |

**为什么必须分这四层**：把 L2/L3 留在分母里，会把"规则没实现"和"规则无效"混成一个数字。
例如 17 项基线里工程化 8 项、首版只实现其中 5 项——若分母用 8，召回率 = 62.5%，
但这 62.5% 里**没有一项是"规则实现了却没查出来"**。这个数字会误导人去改规则，而真正该做的是实现规则。

### 10.6 产出六个数字

```
L1 总数 / L1 命中        ← 首版规则库真实水平的唯一有效指标
  ├ 工程化召回率 = L1 命中 ∩ engineering / L1 总数 ∩ engineering
  └ 语义召回率   = L1 命中 ∩ semantic     / L1 总数 ∩ semantic   ← 预期为 0，如实标注"不覆盖"
L2 清单（规则未实现）    ← 单列，是"待办"不是"缺陷"
L3 清单（无规则，能力外）← 单列，是不覆盖声明的依据
漏报清单 = L1 中未命中   ← 最危险，逐条看
未匹配清单 = 工具报了基线没有 ← 人工定性为真阳性 / 误报
误报率 = 定性为误报数 / 工具总报告数 ← 建议先只统计 blocker 级，避免人工量爆炸
```

**分层统计，绝不混合报告。** 混在一起报会让数字好看但误导。

### 10.7 ⚠️ 首版样本量预警（基于 17 项基线）

按首版规则范围（A/B/C/G/I 五组 P0）逐条归类：

| 层                | 条目                                                         | 数量  |
| ----------------- | ------------------------------------------------------------ | ----- |
| **L1 规则范围内** | K-01(B01) K-02(C01) K-03(C02) K-04(C06，**已由 P1 提升**) K-05(C04) | **5** |
| **L2 规则未实现** | K-08(C07 是 P2) K-09(F05 是 P2，且 F 组不在首版五组)         | 2     |
| **L3 无规则**     | K-06 K-07 K-10~K-17                                          | 10    |

> 校验：L1 5 + L2 2 + L3 10 = 17 ✅（**若将来改动规则范围，必须重新校验这个加法**）

**结论：17 项基线里，首版真正能验证的只有 5 项，且全部是"缺失型"（某文件/目录不存在）——这是规则库中最容易的一类。**

首版大概率会跑出 5/5 = 100%，但**这个 100% 不能证明规则库有效**，只证明了"它能发现一个文件不存在"。

### 10.8 ⭐ 基线补充采用三段法（不依赖人的记忆）**【必须遵守】**

```
第一段：扫描器自动提候选
        S1 扫描器跑一遍 v1，输出所有 finding 作为候选条目

第二段：人逐条确认
        确认"这条是真问题还是误报"，过滤候选

第三段：定向独立核查（★ 不可省略）
        拿着规则定义做窄查询 ——
        "找所有空函数体"、"找所有 except: pass"、"找所有循环 import"
        用独立 grep / 独立脚本捞一遍，与第一段候选做差集
```

**为什么第三段不能省**：只用扫描器提候选**测不出漏报**——扫描器没提出来的，人也不会去确认；而**漏报恰恰是最危险的那一列**。结果是召回率恒等于 100%，这个 100% 是虚空。

**为什么第三段是便宜的**：它不是开放式审计（那是几天的活），而是**窄查询**（几分钟一条规则）。

#### 为什么不用"人照着规则回忆"生成条目

- 维护者对"哪里有存根/循环 import"没有可靠记忆
- **更关键**：人知道规则 ID，照着规则回忆 = **反推答案**。这样测出的召回率是虚的——你只会想起那些"规则本来就能查到"的例子，而漏报清单里恰恰是"规则查不到"的那些。

#### 定向核查要脚本化 **【必须遵守】**

第三段的窄查询**必须落成可重复执行的脚本或 grep 配方**（建议 `tests/fixtures/verify_recipes/`）。理由：

1. 可重跑（规则改了要重跑）
2. 可审计（事后能查"这条基线是怎么来的"）
3. 下次给别的项目建基线时直接复用

#### 诚实的局限（必须写进召回率报告）

```
1. 首版验证的是规则库的下限，不是上限。
2. 定向核查理论上也可能漏（窄查询的覆盖面取决于配方质量）。
3. 因此：L1 命中率高不代表规则库完备，只代表"已验证的那部分没问题"。
```

## 12. 实现备注（骨架阶段发现的有长期价值的结论）

> 本节来自一次骨架验证。结论本身与具体代码无关，但**漏掉会让 S2 误报或让数字失真**，故作为设计约束保留。
> 除标注【必须遵守】的条目外，其余为【建议】。

### 12.0 环境实测结论 **【背景】**

| 项     | 实测                        | 影响                                                         |
| ------ | --------------------------- | ------------------------------------------------------------ |
| Python | 3.10                        | ❌ **无 stdlib `tomllib`**（3.11+ 才有）→ 需 `tomli` 兜底：`try: import tomllib / except: import tomli as tomllib` |
| git    | 2.34                        | worktree / archive 均支持                                    |
| 已装   | `tomli` `PyYAML`            | 可用                                                         |
| 未装   | `pytest` `typer` `networkx` | pytest 仅 dev 需要；**networkx 不需要**（图算法手写约 40 行） |

**运行时依赖应尽可能为零** **【建议】**：工具必须在**自己的环境**里跑，**绝不能装进被审计项目的环境**——否则审计 v1 就得先污染 v1。`tomli` 是唯一例外，且仅 py<3.11 需要。

### 12.1 只读的结构性保证：文件访问层只暴露读 API **【必须遵守】**

**问题**：S1/S2 承诺"只读不侵入仓库"。但承诺靠人守，一次疏忽就破了。

**做法**：所有文件访问走**单一模块**，该模块**只导出读函数**（读文本 / 遍历 / 判存在），不导出任何写能力。扫描链路上的代码**根本拿不到写文件的 API**。

全项目**唯一**的写入口是产物目录模块，职责单一，一眼能审完。

**为什么比"承诺"可靠**：承诺是约定，没有 API 是结构。代码里不存在的东西，不会被误调用。

**配套**：应有专项测试验证"扫完仓库后 git status 仍干净，且所有文件 mtime/size 指纹不变"。

### 12.2 S1/S2 边界：事实 vs 判定 **【必须遵守】**

> **S1 只采集事实，不做判定。**

| S1 采集的事实                     | S2 才做的判定        |
| --------------------------------- | -------------------- |
| `constraints_file.exists = false` | `C04 无约束文件`     |
| `import_graph.cycles`             | `D04 循环 import`    |
| `test_cmd.verified = false`       | 测试门禁是否可信     |
| `toolchain.test_cmd = null`       | `B01 无测试`（部分） |
| `q6_signals.any = false`          | 1.5 的不覆盖声明     |

**为什么这条边界必须写死**：不清的话 S1 会不知不觉长成 S2——每加一条规则就顺手在扫描器里判一次，最后扫描器和审计器职责重叠，且无法单独测试"事实采集"是否正确。

**推论**：S1 的产出里**不应出现任何规则 ID**。

### 12.3 import 图必须区分"模块"与"符号" **【必须遵守】**

**问题**：`from pkg.util import load` 里的 `pkg.util.load` 是个**函数**，不是模块。

**后果**：不区分的话，S2 的 **A04（import 的模块在仓库中不存在）会对每一个跨模块函数调用全部误报**。一次自审计就产生 4 条此类误报，规模稍大的项目会淹没报告。

**做法**：import 图的每条 unresolved 记录带 `as_symbol` 字段：

```json
{"from": "acme.pipeline", "target": "acme.schema.validate",
 "kind": "unknown", "as_symbol": true, "file": "src/acme/pipeline.py"}
```

- `as_symbol = false`：`import x.y` 或 `from x import y` 中的**模块部分**
- `as_symbol = true`：`from x import y` 中的 **y**（可能是函数/类/常量）

**S2 的规则实现必须过滤 `as_symbol = true`** 后再判定"模块不存在"。

### 12.4 `tests/` 目录下的文件不都是测试 **【必须遵守】**

**问题**：判定"某文件是不是测试文件"时，常见写法是"父目录叫 `tests` 就算"。

**后果**：`tests/conftest.py`、`tests/helpers.py`、`tests/fixture_repo.py` 这类辅助文件也被当成测试，进而在 Q2 中被当作**"已通过的测试"候选推荐给用户去勾选**——用户一勾，就把 `conftest.py` 锁进了禁改清单，S4 直接无解。

**做法**：**只按文件名判定**（`test_*.py` 或 `*_test.py`），不看父目录名。

### 12.5 `--exec-probe` 默认关 **【必须遵守】**

**理由（用户裁定，推翻了"默认开 + timeout"的原建议）**：

1. `pytest --collect-only` 会 import 测试模块并**执行模块级代码**，等于在别人仓库里执行任意代码
2. **timeout 防不住副作用**——写文件、发网络请求、读环境变量都会发生
3. 源项目 v1 无测试，首版这条根本跑不到
4. **安全默认：执行任意代码不该是默认行为**

**配套约束**：

- 未验证时如实标 `degraded`，**不把"没验证"说成"已验证"**
- 开启时**只在快照目录（仓库外）执行**；若同时未指定 `--ref`，必须打印警告
- toolchain 的三个状态必须严格分离（见 12.6）

### 12.6 toolchain 探测：三个状态不可混为一谈 **【必须遵守】**

| 字段               | 含义                                     |
| ------------------ | ---------------------------------------- |
| `cmd = null`       | 探测不到命令。**绝不编造**               |
| `binary_available` | 二进制在 PATH 上（安全，不涉及仓库代码） |
| `verified`         | **只有真跑过才为 true**                  |
| `suggested`        | 工具推荐但**未验证**的命令，供 S4 参考   |

**最常见的错**：`binary_available = true` 就置 `verified = true`。那是编造已验证——后面所有验收都建立在假通过上。

**额外陷阱**：实跑"通过"但收集到 0 个用例（静默零收集）时，`verified` 必须置 **false** 并记录原因。判定交给 S2 的 B03。

**junitxml 的两个坑** **【建议】**：

1. pytest ≥ 8 的 junitxml **不带 `file` 属性**，需从 `classname`（如 `tests.test_core`）反推相对路径（逐个前缀试探，命中最长的那个）
2. **收集期错误不是一个用例**——它会以 `testcase` 形式出现，直接计入会让"收集到 1 个用例"这种假象出现（实际是 1 个收集失败）

### 12.7 worktree vs archive 的取舍 **【建议】**

| 方案                 | 对源仓库写入                  | 残留风险               | 快照内有 `.git`？ |
| -------------------- | ----------------------------- | ---------------------- | ----------------- |
| **worktree**（默认） | ⚠️ 写 `.git/worktrees/` 元数据 | 崩溃会残留，需 `prune` | ✅ 有              |
| **archive**          | ✅ 零写入                      | 无（tmpdir 而已）      | ❌ 无              |
| clone --shared       | ✅ 零写入                      | 源仓库被删则快照损坏   | ✅ 有              |

**推荐：worktree 为主（默认），archive 一并实现**（成本约 10 行：`git archive <ref> | tar -x -C <tmp>`）。

- worktree 默认：快照自带完整 git 上下文，S2 的 **G 组**（`.git` 体积、已跟踪大文件、密钥扫描）才能跑
- archive 留给"审计别人仓库、绝对不能留痕"的场景
- 不选 clone --shared：`--shared` 有上述坑，且比 worktree 慢

**关键实现约束** **【必须遵守】**：

> **git 事实始终从源仓库采集，文件内容从快照目录扫描。**
>
> 因为 archive 快照里没有 `.git`——若从快照目录采 git 事实，会得到一片 `null`，
> 而 `rev_count` / `branch` / `clean` 这些恰恰是 G 组和决策 #8 的输入。

**worktree 残留的缓解**：`try/finally` 保证 `git worktree remove --force` + `prune`；若进程被 SIGKILL，用户手动 `git worktree prune` 即可（不动源码、不动 refs、不动工作树）。tmpdir 一律建在仓库之外。

### 12.11 两条已知局限（如实标注）

1. **Q6 信号会误命中**：任何名字含 `baseline/expected/golden/reference` 的 `.json/.npy/.csv` 都被算作"数值基线"信号。工具自己的 `tests/fixtures/baseline.json` 就会命中。阈值是 ≥2 个信号才建议 Q6 默认开，单条误命中影响有限，**但别把它当强信号**。
2. **`--exec-probe on` 且无 `--ref` 时是在目标工作目录里跑被测代码**（会打印警告）。建议始终配合 `--ref`。

### 12.12 两条实现阶段定死的口径（踩过坑才写下来）

#### ① 仓库根的判定只能用 `git rev-parse --show-toplevel` **【必须遵守】**

不要写成"逐级往上找哪个父目录有 `.git`"。

**为什么**：那种写法对「目标目录**自身**就是仓库根」的情况必然漏判 ——
`.git` 就在目标目录里，往上找反而什么也找不到。实测事故：断言
`v1-reference` 不在 git 仓库里（`git rev-parse --show-toplevel` 返回它自己），
于是 vcs 字段族被当成非仓库、G 组整体失效。

`git rev-parse --show-toplevel` 自己会向上查找并报告**真实的**仓库根：
自身即根返回自身，是子目录返回祖先，一个 API 覆盖两种情形。

#### ② 模块名可以有多个合法写法：别名 + 重名即不解析 **【建议】**

只按"仓库根相对路径"算点分名会让整类 import 被误判成不存在，所以要认两种 source root：

| 情形 | 证据 | 例 |
| ---- | ---- | -- |
| 打包声明的 source root | `setuptools.packages.find.where` / poetry `from` | `src/acme/core.py` 也可写作 `acme.core` |
| **入口脚本所在目录** | 文件里有 `if __name__ == "__main__"`（`python x.py` 时该目录进 `sys.path[0]`） | `src/modules/train.py` 里的 `from language_module import ...` |

**重名即不解析**：两个 source root 出现同名模块时不猜是哪一个（猜错比不说更糟），
该别名直接丢弃，目标留在 `unresolved_imports` 里等人工确认。

**仍有覆盖不到的情况**：既无打包声明、又无 `__main__` 守卫的纯脚本目录
（典型：`archives/` 下一堆随手写的探索脚本），其兄弟 import 会被标成
`third_party`。这是刻意的保守——A04 误报比漏报更伤工具的可用性。

**顺带一个便宜的自证** **【建议】**：工具自己应该有 `pyproject.toml` + lint 配置 + `tests/`。一个专门检查"别人有没有 pyproject"的工具，自己没有会很尴尬——而且自审计一遍就是现成的冒烟测试。

## 14. S5 最小切片：A / B / E 三格（首版之外的第一刀）

> **定位**：不是"让工具改代码"，而是 **工具产指令 → AI 改代码 → 工具读事实判检查点**。
> 工具全程不执行 git 写操作、不改目标仓库源码。
> 只做三格，**不做** S4 规划算法、问卷、C 格（R7）、D 格（R4）、F 格（R8/R9）、S6/S7、多轮回环。

### 14.1 输入

| 输入 | 说明 | 不满足时 |
| ---- | ---- | -------- |
| `--target <path>` | toy 项目；**必须是 git 仓库**（否则 E 格判不了） | 报错退出 |
| `--plan FILE` | **手写单阶段**计划（替代 S4），见 14.2 | 报错并**指明缺哪个字段** |
| 已有 `scan.json` | `project.*` 占位符从它取 | 提示先跑 `scan` |
| `.upgrade/state.json` | 首次自动初始化 | — |

### 14.2 plan schema 与两条硬约束

```json
{"schema_version": 1,
 "stage": {"id": "s1", "type": "ai",
           "writes": ["src/acme/core.py"],
           "forbidden_paths": ["tests/", "CODEBUDDY.md"],
           "behavior_spec": "只描述行为，不指定名字"}}
```

**【必须遵守】**

1. **`schema_version` 必填（首版 = 1）**；缺字段时报错并**指明缺哪个**（不猜、不默认）
2. **`writes[]` 是相对 `--target` 根的路径，不支持 glob** —— glob 会让 B 格的越界判定变模糊
   （`src/**/*.py` 到底算不算越界？判定一旦含糊，检查点就失去意义）

### 14.3 每格的输出与检查点

| 格 | 机械部分（工具做） | 输出 | 检查点（工具读事实判） |
| -- | ------------------ | ---- | ---------------------- |
| **A** 只读核对（R1+R2+R3b） | `dep_table` / `contract_snapshot` / `constraints_expected`（锚点**按 ID 计数**，4.2②） | `.upgrade/steps/<stage>.A.md` | ① `dep_table` 无 `stub`/`missing` → 通过；有 → 不推进，输出"补实现阶段"指令 ② **运行前后零改动**（对 A 格渲染时记录的指纹） |
| **B** 实现 | 真实路径 + 只描述行为 + 契约快照 + 禁改路径 + 证据协议 | `.upgrade/steps/<stage>.B.md` | ① `git status --porcelain` 的改动路径**全部落在 `writes` 内** ② **未触碰 `forbidden_paths`**（路径前缀比） ③ **`writes` 非空却零改动 → 判未完成** |
| **D** 实跑验收（R4） | 生成验收命令（**只生成不执行**） | `.upgrade/steps/<stage>.D.md` + 证据日志（仓库外） | 读证据日志，**按命令类型**判要求（退出码为公共项；见 14.9②） |
| **E** 提交拆分（R5+R6） | 按路径分类 `commit_type` → 逐条 `git add <path>`（**明令禁 `git add -A`**）→ 生成 message | `.upgrade/steps/<stage>.E.md` | ① `git status --short` 为空 ② `rev-list --count` 相对渲染时 +N ③ 每个提交 **subject 逐字一致**（body 允许自由） |

**E 格的两条边界**

- **无改动可提交时输出"无需提交"**，绝不输出空的 `git add`
- **subject 逐字一致，body 允许自由**：工具生成的是 subject，body 可自行补充说明

**⚠️ 前置条件：开工时目标工作树必须干净（决策 8）**

B 格的判据是"改动路径全在 `writes` 内"。**若开工前工作树就有未提交改动**，
那些路径不在 `writes` 里 → 被判越界 → 误报阻塞。所以：

```
进入 A 格前检查 git status --porcelain 为空；
不为空 → 停下提示（"先提交或 stash 再开工"），不渲染任何指令块
```

这同时是 A 格"运行前后零改动"有基准的前提。

### 14.4 两条硬规矩

- **渲染铁律（6.2）**：三层占位符 `project.*` / `stage.*` / `facts.*`；
  任何未解析的 `{{...}}` → **拒绝输出并报错**，绝不原样交给 AI
- **单步推进（3.1）**：一次运行最多推进一格；检查点不过就停在原格输出诊断

### 14.5 `--cell` 的护栏（同 `--exec-probe` 的道理）

- 重跑当前格 / 回退 → 不警告
- **强制**向前跳到当前格之后的格 → **打印 WARNING**，并在 `state.json` 记 `forced = true`
- 理由：**绕过门禁不该是静默行为**

### 14.6 切片自己的验收清单

- [ ] A→B→E 连续推进；`state.json` 每步最多进一格
- [ ] 三份指令块**零未渲染占位符**（渲染铁律）
- [ ] 四个"应拦下"的分支都能判出且不推进：A 格 `stub`、B 格越界、
      **B 格 `writes` 非空却零改动**、E 格 subject 不一致
- [ ] 工作树不干净时停在 A 格之前
- [ ] E 格无改动时输出"无需提交"
- [ ] `--cell` 向前跳时打印 WARNING 且 `state.json.forced = true`
- [ ] 工具运行前后目标仓库源码不变（指纹 + `git status`）；产物只落 `.upgrade/`（默认仓库外）

## 14.9 D 格：实跑验收（R4）

**五条设计约束【必须遵守】**

### ① 与 E 格一致：只生成命令，不执行

```bash
{ <test_cmd> 2>&1; echo "RP_EXIT_CODE=$?"; } | tee <evidence_path>
```

由 AI / 人执行，工具下次运行读日志判定。**必须这样**：`scan --exec-probe` 默认 off 就是
"工具不执行被测代码"，D 格若自己跑测试就与那条冲突。**人执行 + 工具读证据 = 指挥官模式。**

两处与 4.2① 字面写法的**必要偏离**（都已在 `facts.py` 注明）：

- **证据路径在仓库外**：4.2① 写 `.upgrade/evidence/<stage>.log`，但决策 #29 / 9.5
  已把产物移到仓库之外；若按字面写，D 格会把日志写进被审计仓库，直接违反只读承诺。
  所以指令里给**绝对路径** `<out>/evidence/<stage>.log`
- **加 `RP_EXIT_CODE=$?` 标记**：`tee` 之后的管道退出码不可靠，必须显式记进日志，
  否则判定里的"退出码"拿不到

### ② 按**命令类型**决定证据要求（判据来自命令本身，缺一即判未完成）

> **2026-10-11 修正（见 14.11）**：原先把"用例数"写成对**所有**命令的硬要求 —— 那是 pytest
> 形状的，任何非测试命令（lint / TOML 校验 / import smoke）都凑不出用例数 → D 格永远判未完成，
> 哪怕命令成功。现在改为按命令类型自动判定，**人只给命令，不额外声明期望（不加 `--expect`）**。

| 命令类型 | 识别 | 证据要求 |
| -------- | ---- | -------- |
| 测试运行器 | 命令含 `pytest` / `unittest` / `py.test` | 退出码 0 **且**用例数（`N passed` / `collected N items`）；**0 个用例算失败** |
| lint / 类型 / 格式化 | 命令含 `ruff` / `mypy` / `flake8` / `pylint` / `black` / `isort` … | **只要退出码 0** |
| 其它 | 以上都不含 | 退出码 0 **且**至少一行非空输出 |

**退出码是所有命令的公共要求**。**无证据文件 = 未完成**，并**重发 D 格指令**。

### ③ 无可用 test_cmd 时不能静默跳过

标 `state.needs_manual_acceptance = true` 并**阻塞**（8.3 的 C4），提示人用
`--test-cmd "<命令>"` 给出验收命令。**不渲染 D 块** —— 没有命令的 D 块是空壳。

### ④ 检查点必须配"故意让它失败"的用例（见 14.10）

### ⑤ `external` 状态不能静默

src 布局若无打包声明，`from acme.schema import ...` 会被判 `external`（A 格不阻塞）。
**这个降级必须在指令块里显式列出**（A 块里单列一节），不能只在日志/表格里。

理由：**R1 是最高价值规则，它悄悄退化无人知道。**

## 14.10 规矩：每个检查点必须配"故意让它失败"的用例 **【必须遵守】**

只测通过路径**测不出失效**。以下检查点都曾出现"看起来在工作、其实永远通过"的风险：

| 检查点 | 反向用例（必须存在） |
| ------ | -------------------- |
| A 格 `dep_table` | 依赖是存根时拦下 |
| A 格零改动 | 渲染后源码被改动 → 拦下 |
| B 格越界 | 改 `writes` 之外的文件 → 拦下 |
| B 格禁改路径 | 改到 `forbidden_paths` → 拦下 |
| B 格零改动 | `writes` 非空却没动文件 → 拦下 |
| D 格证据 | 缺日志 / 退出码非 0；测试命令再分：零用例 / 读不出用例数；普通命令再分：只有标记无输出 —— 都要拦下 |
| E 格 | subject 不一致 / 提交数不符 / 工作树脏 —— 都要拦下 |
| `--cell` 向前跳 | 向前跳要警告 + `forced=true`；**重跑与回退不得警告** |
| 渲染铁律 | 残留 `{{}}` 必须报错 |

**新增任何检查点时，必须同时交一条"故意失败"的用例** —— 否则这条检查点等于没验过。

## 14.11 真实试验（v1 clone）暴露的边界：创建类任务

首次端到端试验用 `/tmp/rp-toy-v1`（v1 的 clone 副本）跑基线任务 **K-02 补 pyproject.toml**
（`writes = ["pyproject.toml"]`，单文件、真实有价值的工程化补课）。结论如下 —— 这段是本次试验
最有价值的产出，**比"跑通了"重要得多**：

> 工具在改已有 Python 时最亮（R1 依赖闭合 + R2 契约快照都满血）。但新建非 Python 文件时，
> 两个核心价值同时归零，偏偏门禁在这情形下是错的。

具体表现（修复前）：

- **A 格把"待创建的目标"当成"缺失的依赖"**：`dep_table` 对不存在的目标文件产出一条
  `missing` 行，`_gate_a` 因此拦下 —— 而"要建的文件当然还不存在"。K-02 恰好落在这个洞里，
  必须用 `--cell b` 强跳才走得动，而强跳会绕过 R1，等于这道门白设。
- `writes` 是非 Python 文件时，`dep_table` 走不到依赖解析、`contract_snapshot` 为空 ——
  R1 / R2 两个核心价值同时归零，正是上面那句话说的情形。

### 两条修复（2026-10-11，均按"能从事实推断的就不让人声明"，决策 6）

1. **A 格区分"新建"与"依赖缺失"**：目标文件**不在 `git ls-files` 里、磁盘也不存在** → 判为新建，
   **不产 `missing` 行**。判据用 git 事实自动推断，**不加 `creates` 字段** ——
   加字段等于让 plan 作者多一个可能填错的东西，写错的后果和现在一样严重。
2. **D 格按命令类型自动决定证据要求**：`pytest` / `unittest` → 要用例数（0 个算失败）；
   `ruff` / `mypy` / `flake8` 等 → 退出码 0 即可；其它命令 → 退出码 0 + 至少一行非空输出。
   判据来自**命令本身**，**不加 `--expect` 参数** —— 人只给命令，不额外声明期望。

修复后同一任务**无需任何强跳**即可 A → B → D → E 走完。

### 一句话定位当前能力

对**修改已有 Python** 的任务，工具的门禁是有意义的；对**创建新文件**的任务，R1 / R2 无从发力，
门禁只应起"记录 + 收口"作用，不应拦路。**S4/S5 完整版动工前，必须先想清这个边界的含义。**
